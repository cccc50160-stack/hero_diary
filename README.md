# Life RPG — Telegram Mini App

Твой дэшборд, переведённый с одного самодостаточного HTML-файла на архитектуру мини-аппа:
фронтенд (`public/index.html`) + бэкенд (`server/`) + база данных Postgres, где прогресс
каждого пользователя хранится по его Telegram ID — то есть сразу многопользовательская,
как ты и просил.

## Структура

```
life-rpg-miniapp/
  public/
    index.html        — тот же дэшборд, адаптированный под Telegram + сервер
  server/
    server.js          — Express-сервер: отдаёт фронтенд + API
    db.js               — подключение к Postgres, чтение/запись состояния, мировой босс
    telegramAuth.js      — проверка подписи Telegram (кто есть кто)
    reminders.js          — логика вечерних пушей: кому, когда и каким текстом
    schema.sql             — структура таблиц
    test-auth.js            — автотест проверки подписи (без интернета)
    test-reminders.js        — автотест логики напоминаний (без интернета)
    package.json
    .env.example
```

### API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/health` | Живой ли сервер |
| `GET` | `/api/state` | Прогресс текущего игрока |
| `PUT` | `/api/state` | Сохранить прогресс |
| `GET` | `/api/worldboss` | Текущий общий босс: HP, максимум, число побед, номер волны |
| `POST` | `/api/worldboss/damage` | Урон (`+`) или его возврат (`−`) по общему боссу |
| `GET` | `/api/cron/reminders?key=` | Дёргается внешним кроном, рассылает вечерние пуши |

Всё, кроме `/api/health` и крона, требует подписанный `Authorization: tma <initData>`.
Крон вместо этого проверяет общий секрет `CRON_SECRET` (сравнение постоянное по времени).

## Интерфейс

Четыре экрана вместо одной длинной ленты — переключаются нижней навигацией:

- **Сегодня** — шапка героя, строка главы, кольцо итога дня и ежедневные задания.
- **Задания** — общий рейд-босс, личные боссы, разовые и исполненные.
- **Герой** — аватар, спутник, умения, глава целиком, достижения.
- **Ещё** — сводка, лавка наград, три трекера и настройки, все свёрнуты в строки.

Ежедневных заданий около тридцати, и сокращать их нельзя: приложение общее, у разных
людей разные темы. Поэтому длину решает не вырезание, а группировка — тема, где сегодня
уже есть движение, раскрыта, остальные свёрнуты в одну строку. Итог: было 6100px одной
лентой (≈15 экранов телефона), стало 1050–1600px на экран.

### Темы

Две: **Ночь** (тёмная) и **День** (светлая бумага). Раньше почти чёрный фон соседствовал
с ярко-бумажными панелями — вечером это било по глазам; теперь панель отличается от фона
на пару ступеней, а не на порядок, в обеих темах.

Важное правило кода: **тема задаёт только CSS-переменные и никогда — вёрстку**. Блоки
`body[data-theme="..."]` содержат исключительно переменные, компоненты ниже пользуются
только ими и не знают, какая тема активна. Поэтому добавить новую тему (например, под
другую игру) — это дописать один блок переменных в CSS и одну строку в реестр `THEMES`
в скрипте. Ни один селектор компонента при этом трогать не нужно.

## Общий рейд-босс

Личные боссы в списке заданий никуда не делись — это твоя тропа. Поверх них есть **один
Долгий Штиль на всех игроков сразу**: строка в таблице `world_boss`, по которой бьёт каждый.
Любое выполненное задание категории «боссы» наносит ему тот же урон, что и личному боссу;
снятая галочка так же честно возвращает HP обратно (иначе «поставил-снял» было бы бесконечным
источником урона). Когда HP доходят до нуля, босс тут же поднимается снова, крепче:
`5000 + число_побед × 1500`.

Урон применяется в транзакции с `SELECT ... FOR UPDATE`, поэтому одновременные удары
нескольких игроков не теряются. Один запрос не может нанести больше 200 урона и меньше −200.
Панель на фронтенде показывает HP, номер волны, счётчик побед и твой личный вклад в текущую
волну. Если сервер недоступен — панель честно об этом пишет, а личный прогресс считается как
обычно: общий босс сознательно сделан необязательной надстройкой.

## Вечерние напоминания

Бот присылает не больше одного сообщения в сутки, только в окне 19:00–23:00 по Москве, и
только если есть что сказать: либо остались незакрытые дневные задания, либо стрик доживает
последние часы. Отправляет их не таймер внутри процесса (на бесплатном Render процесс просто
засыпает), а внешний пингер, который раз в час дёргает `/api/cron/reminders`. Настройка —
в `DEPLOY.md`, раздел 7.

## Как это работает

- Пользователь открывает мини-апп внутри Telegram → Telegram сам передаёт подписанные данные
  о пользователе (`initData`) в `Telegram.WebApp.initData`.
- Фронтенд шлёт эти данные на сервер с каждым запросом (`Authorization: tma <initData>`).
- Сервер проверяет подпись **своим** секретным токеном бота — подделать её нельзя, не зная
  токена. Так сервер узнаёт, кто есть кто, без паролей и логинов.
- Состояние (весь тот большой JSON, который раньше скачивался файлом) хранится в Postgres,
  по одной строке на `telegram_id`. Автосохранение — через ~1.2 секунды после любого
  изменения (квест отметил, стат прокачал и т.д.), без единого клика.
- Кнопки «Резервная копия в файл» / «Восстановить из файла» остались — это просто ручной
  бэкап поверх автосохранения, на всякий случай.
- Если открыть `index.html` НЕ в Telegram (например, в обычном браузере при разработке) —
  всё работает точно как раньше: без сохранения на сервер, только в памяти вкладки. Это
  безопасный режим для локальной проверки вёрстки.

## Что уже проверено, а что — нет (важно, честно)

В моей текущей песочнице оказался заблокирован доступ к `registry.npmjs.org` (это ограничение
именно этой сессии, не самого кода) — поэтому `npm install` для `express`/`pg` здесь не
срабатывает, и я не смог запустить сам `server.js` живьём в этой песочнице. То, что я **реально
проверил напрямую**:

- **Проверку подписи Telegram** (`telegramAuth.js`) — юнит-тестами на встроенном `crypto`
  Node.js, без единой внешней библиотеки: валидная подпись принимается, подделанная,
  просроченная или подписанная чужим токеном — отклоняется. Прогнать самому: `npm test`
  внутри `server/` (тест не требует интернета и express/pg).
- **Сами SQL-запросы** (вставка/обновление/чтение) — напрямую через `psql` на локальном
  Postgres: вставка нового пользователя, повторное сохранение (апдейт), чтение
  существующего и несуществующего пользователя — всё отработало верно.
- **Весь клиентский код синхронизации** (`fetch` на `/api/state`, дебounce, поведение при
  первом заходе/повторном заходе/вне Telegram) — через Playwright, но не против настоящего
  `server.js`, а против временной заглушки с точно таким же HTTP-контрактом (тот же
  `telegramAuth.js`, тот же формат запросов/ответов), в памяти вместо Postgres. Полный цикл
  «зашёл первый раз → отметил квест → перезашёл → прогресс на месте» — работает.

Единственное, что я не прогнал живьём именно в связке — это сам `express` + `pg` слой
(`server.js`/`db.js` целиком). Код там стандартный, без нестандартных трюков — это ровно тот
паттерн, который используют почти во всех Node-бэкендах такого рода, поэтому риск низкий, но
это стоит знать: первый реальный прогон будет уже у тебя на хостинге. Первым делом после
деплоя стоит просто открыть мини-апп и проверить, что прогресс правда сохраняется —
дальше см. `DEPLOY.md`.

### Редизайн — что проверено

Сквозным тестом в headless-браузере против заглушки с тем же HTTP-контрактом (тот же
файл `public/index.html`, что уезжает в прод): стартует «Сегодня», остальные экраны
скрыты; ежедневные сгруппированы по темам и **ни одно не потеряно**; темы сворачиваются
и разворачиваются; отметка задания пересчитывает кольцо дня, счётчик темы и XP, а снятие
галочки откатывает всё обратно; переключение всех четырёх экранов; панель рейд-босса и
урон по нему через ежедневное задание, включая возврат урона; сетка умений, спутник,
глава и компендиум достижений; сворачивание разделов в «Ещё»; смена темы с сохранением
на сервер; настройка трекера сна; добавление своего задания. За весь прогон — ни одной
ошибки в консоли.

### Мировой босс и напоминания — что проверено

- **Логика урона по мировому боссу** (`db.js`) — прогнана против настоящего Postgres:
  обычный урон, клэмп одного удара до ±200, лечение с упором в максимум HP, симметричность
  «поставил/снял галочку», смерть ровно в ноль и в минус, респавн с формулой
  `5000 + побед × 1500`, отбрасывание нуля и мусора, усечение дробных значений. Отдельно —
  двадцать **одновременных** ударов: суммарный урон сошёлся до единицы, то есть блокировка
  строки работает и параллельные удары не теряются.
- **Логика напоминаний** (`reminders.js`) — юнит-тесты без интернета, `npm test`: молчим,
  когда всё закрыто или день уже засчитан; считаем задания незакрытыми у того, кто сегодня
  не заходил (сброс дневных происходит на клиенте, и вчерашние галочки нельзя принимать за
  сегодняшние); предупреждаем о стрике только если серия правда живая; не считаем
  заблокированные задания; склонение «день/дня/дней»; мусор на входе не роняет крон.
- **Фронтенд общего босса** — через Playwright против заглушки с тем же HTTP-контрактом:
  панель тянет HP с сервера, выполненное задание шлёт ровно один запрос урона, снятая
  галочка возвращает ровно столько же, вклад и ачивка доезжают до сохранённого состояния,
  вне Telegram панель прячется, при мёртвом сервере показывает честную заглушку и не мешает
  остальному дневнику.

## Что нужно от тебя

1. **Токен бота.** У @BotFather: `/newbot` → имя, username → получаешь токен вида
   `123456789:AAExample...`. Это и есть `BOT_TOKEN`.
2. **Postgres.** Проще всего — бесплатный [Neon](https://neon.tech) или
   [Supabase](https://supabase.com): регистрация → создать проект → скопировать
   connection string (`postgres://...`). Это и есть `DATABASE_URL`.
3. **Хостинг под сервер** (не просто статику — нужен постоянно работающий процесс):
   [Render](https://render.com) или [Railway](https://railway.app), у обоих есть
   бесплатный старт. Подробности — в `DEPLOY.md`.
4. После деплоя — **URL мини-аппа** в @BotFather: `/mybots` → бот → *Bot Settings → Menu
   Button* → вставить https-адрес, который выдаст хостинг.

Дальше — по шагам в `DEPLOY.md`.
